# 観点: 仕様書と実装のずれ

`Docs/` 直下の .md（`archive/` は除く）の記述を、今の実装に合わせて直す。
CLAUDE.md では「仕様書が正」だが、この観点で扱うのは **実装のほうが新しく、ドキュメントが追いついていない** もの。
どちらが正しいか判断できないもの（実装がバグかもしれないもの）は勝手に直さず「要確認」にする。

分担は `plan_chunks.py --mode docs` で、ドキュメントを見出し単位（約300行）に区切る。haiku は担当の範囲を読み、書かれている事実（数値・画面の流れ・クラス名・ファイル名）をコードで確かめる。

## 事前に確認すること

1. **PLAN_*.md（当時の計画）**: 計画と違う実装になった箇所をどう扱うか
   - 推奨: 本文は書き換えず、該当箇所に「（実装では〜）」と注記する。計画書は経緯の記録なので
2. **STORY_ROADMAP.md の進捗表記**: 実装済みのものを「済」に更新してよいか
   - 推奨: 更新する
3. **仕様書にない機能が実装にある場合**: 仕様書に書き足すか
   - 推奨: 書き足さず「要確認」で一覧に出す（範囲が広がりやすいため）
4. **仕様書 §10「フォルダ・クラス構成」**: 実際のファイル構成に合わせて書き換えてよいか
   - 推奨: 書き換える

## 解析プロンプト

```
あなたは乱戦！ペンモンスクランブル（Unity / C#）の仕様書と実装を突き合わせる担当です。観点は「ドキュメントの記述が今の実装と合っているか」だけに絞ってください。
このタスクではファイルを編集しないでください。読んで指摘するだけです。

## 担当範囲
{ファイル名と行範囲}（Read の offset/limit で読む）

## 方針（ユーザーと決めたこと）
{手順2で決めた方針}

## 手順
1. 担当範囲を読み、確かめられる事実を拾う: 数値（ダメージ倍率・ターン数・確率・HP など）、画面の流れ・ボタン名、クラス名・ファイル名・フォルダ構成、データの数（種の数・技の数など）。
2. それぞれを Assets/_Project 以下のコードで grep して確かめる。数値はバランス定義クラスや定義表（Balance・Definitions・Table などの名前のファイル）にあることが多い。
3. 合っていないもの、コード上に存在しないクラス・ファイルを指しているものを書く。確かめられなかったものは書かない。

{common-rules.md の「haiku に必ず渡すルール」}

## 出力
1行1件、次の形式だけで返してください。
- [高|中|要確認] Docs/ファイル:行 | ドキュメントは「〜」、実装は「〜」（根拠: 相対パス:行） | 直したあとの文
確度: 実装の値をコードで確認できた → 高、推測を含む → 中、実装がバグの可能性もある・仕様書にない機能 → 要確認。
指摘がなければ「なし」とだけ返してください。
```

## 修正プロンプト

1つのドキュメントは1体の haiku にまとめて渡す（同じファイルを2体で編集しない）。

```
あなたは乱戦！ペンモンスクランブルのドキュメントを直す担当です。下の「承認済みリスト」の項目だけを直してください。リストにないことは、気づいても直さないでください。
文体（です・ます／だ・である、箇条書きの形）は周りに合わせてください。コード（.cs）は編集しないでください。
```
