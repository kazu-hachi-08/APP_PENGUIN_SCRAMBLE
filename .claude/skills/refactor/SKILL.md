# リファクタリング (refactor)

メインエージェント（あなた）は **指揮役** に徹する。ファイルを読み込んで自分で解析したり、自分で直したりはしない。
解析も修正も `Agent` ツールで `model: "haiku"` のサブエージェントに任せる。
理由: 対象は約4万行あり、メインが読むとコンテキストもコストも膨らむ。haiku に小さく分けて渡すほうが安く、見落としも減る。
その代わり haiku は誤検出（実は使っている関数を「未使用」と判断する等）をしやすいので、メインは「分担」「方針の質問」「承認」「コンパイル確認」で品質を守る。

## 流れ

1. 観点を選ばせる（1回の実行で1観点だけ）
2. 観点ごとの方針を質問する（迷う点がなければ飛ばす）
3. 分担を作る（スクリプト）
4. haiku で解析（並列）
5. 候補一覧を見せて承認をもらう
6. haiku で修正（並列・同じファイルを2体で触らない）
7. コンパイル確認 → 差分の要約を報告

ビルド・テストの最終確認とコミットはユーザーが Unity で行う。ブランチ作成・コミット・PR はしない。

### 1. 観点を選ばせる

ユーザーの依頼文で観点がはっきりしていれば（例:「使ってない関数消して」）その観点で確定し、確認だけ取って進む。
はっきりしなければ `AskUserQuestion`（単一選択）で聞く。1回で1観点に絞るのは、haiku をその観点だけに集中させるため。別の観点は次の実行で。

| 観点 | 参照ファイル |
|---|---|
| コメント・宣言の整理（「フェーズ1」「仕様書§1」等の経緯コメント、重複コメント・重複宣言） | `references/comments.md` |
| 未使用コードの削除（呼ばれていない関数・フィールド・using・クラス） | `references/unused.md` |
| 仕様書と実装のずれ（Docs/ 直下の .md を実装に合わせる） | `references/spec-drift.md` |
| 重複処理の共通化（コピペされたロジックを1か所にまとめる） | `references/duplication.md` |

選ばれた観点の参照ファイルと、全観点共通の `references/common-rules.md` を読む。

### 2. 方針を質問する

参照ファイルの「事前に確認すること」を見て、ユーザーの依頼文や会話から決まっていないものだけ `AskUserQuestion` で聞く（最大4問。推奨を先頭に）。
すべて決まっていれば質問せずに進む。ここで固めた方針は、haiku への指示にそのまま書き込む。haiku は質問できないので、曖昧なまま渡すと勝手な判断で直してしまうため。

### 3. 分担を作る

```bash
python .claude/skills/refactor/scripts/plan_chunks.py --mode code   # コード系の観点
python .claude/skills/refactor/scripts/plan_chunks.py --mode docs   # 仕様書と実装のずれ
```

JSON で「担当名・行数・ファイル一覧」が出る。1担当あたり約3000行（docs は約300行）になるようフォルダ単位で分かれている。
対象は `Common/Scripts`・`Common/Editor`・`Games/100_PenmonScramble/Scripts`・`Games/100_PenmonScramble/Editor`。`Tests/` は修正対象外だが、「使われているか」の確認には読ませる。

### 4. haiku で解析（並列）

担当ごとに `Agent`（`subagent_type: "general-purpose"`, `model: "haiku"`）を **1メッセージでまとめて** 起動する。
プロンプトは参照ファイルの「解析プロンプト」をもとに、次を埋めて作る:

- 担当のファイル一覧（スクリプトの出力をそのまま）
- 手順2で決めた方針
- `common-rules.md` の「haiku に必ず渡すルール」
- 出力形式（下記）。**解析中はファイルを編集しない** と明記する

解析結果の形式（haiku の最終メッセージ）:

```
- [高|中|要確認] 相対パス:行 | 何が問題か | どう直すか
```

`要確認` は haiku が判断できなかったもの。理由を一言添えさせる。

### 5. 候補一覧を見せて承認をもらう

全担当の結果を集め、メインが次を行ってから提示する:

- 重複している指摘をまとめる
- `common-rules.md` の禁止事項（セーブデータ関連など）に触れる指摘は「対象外」に回し、理由を書く
- 確度ごとに並べ、通し番号を振る

提示はファイル別に短く。件数が多いとき（目安30件超）はファイル単位の件数サマリ＋「高」だけ全文、「中・要確認」は番号と1行要約にする。
ユーザーには「全部OK / 番号で除外 / 高だけ」のように答えてもらう。`要確認` は1件ずつ判断が要るので、まとめて質問する。

### 6. haiku で修正（並列）

承認された項目を **ファイル単位でまとめ直して** haiku に割り当てる。

- 2体の haiku に同じファイルを渡さない（同時に Edit すると片方の変更が消える）。複数フォルダにまたがる修正（共通化など）は、ファイルが重ならないものだけ同時に走らせ、重なるものは次の回に回す。
- プロンプトには承認済み項目のリストだけを渡し、「リストにないことは直さない」と明記する。haiku は気を利かせて範囲を広げがちなので。
- 修正プロンプトは参照ファイルの「修正プロンプト」をもとにする。

### 7. コンパイル確認と報告

```bash
python .claude/skills/refactor/scripts/build_check.py
```

`Assembly-CSharp-Editor.csproj` と `PenmonScramble.Logic.Tests.csproj` を `dotnet build` し、エラーだけを出す（意図して消したファイルの CS2001 は除外済み）。
エラーが出たら、該当ファイルを担当した haiku に（`SendMessage` で続きを）エラー文を渡して直させる。2回直して残るなら、その変更を `git checkout -- <file>` で戻し、報告に書く。

csproj は Unity が生成したもので、ファイルを足した・消したときは Unity を開くまで古い一覧のまま。新規ファイルを作った場合はコンパイル確認から漏れるので、報告でその旨を伝える。

最後に `git diff --stat` と差分をもとに、次の形で報告する:

```
## リファクタリング結果（観点: ○○）
- 修正: N件（ファイル M個）／除外: K件
- 主な変更: （ファイル別に1行ずつ）
- 戻した変更・未対応: （あれば理由つき）
- 確認してほしいこと: Unity でのコンパイル・EditMode テスト実行
```

純C#（UnityEngine に依存しない asmdef）のロジックを変えた場合は、CLAUDE.md に従い `Tests/Editor/` のテストが必要かも報告に書く。
